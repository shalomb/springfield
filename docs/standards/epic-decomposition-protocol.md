# Epic Decomposition Protocol (EDP)

**Status:** Active  
**Version:** 1.0  
**Related ADR:** [ADR-007-epic-refinement-and-lisa-lrm.md](../adr/ADR-007-epic-refinement-and-lisa-lrm.md)

## 1. Overview
The Epic Decomposition Protocol governs the structural handoff between agents in the Inner Loop (Lisa → Ralph → Bart). It defines the exact schema for the high-fidelity Epic (`TODO-{id}.md`), the machine-readable scope constraints (`scope.toml`), the execution guardrails (`guardrails-{id}.sh`), and the retrospective feedback loop that drives continuous learning.

## 2. The High-Fidelity Epic: `TODO-{id}.md`
Lisa generates this artifact during the Last Responsible Moment (LRM). It consists of three immutable layers and one mutable working layer for Ralph.

### Template Structure

```markdown
# TODO-td-{id}.md — {Epic Title}

## Intent Layer (Immutable)
**Origin:** Marge's Feature Brief
**User Need:** {Why are we doing this?}
**Acceptance Criteria (BDD):**
- {Gherkin scenarios to be satisfied}

## Approach Layer (Lisa's LRM Decision)
**Chosen Option:** {Description of the selected architectural approach}
**Rationale:** {Why this option won over others}
**Alternatives Rejected:**
- {Option B}: {Why it was rejected}
- {Option C}: {Why it was rejected}

## Constraint Layer (Inherited)
**ADRs in Effect:**
- [ADR-XXX](...) - {Specific constraint to uphold}
**Quality Thresholds:**
- Farley Index minimum: {score}
- Adzic Index minimum: {score}
**Tech Debt Constraints:**
- {Must not worsen X}

## Working Layer (Ralph's Execution)
*Ralph fills this layer bottom-up via TDD. Failing tests become the task list.*
```

## 3. The Machine-Readable Contract

Lisa also generates two machine-readable artifacts alongside the `TODO-{id}.md` to bound Ralph's context.

### 3.1. `scope.toml`
Defines the strict boundaries of Ralph's worktree execution.

```toml
[scope]
modify  = ["list of specific files/directories"]
create  = ["list of specific files/directories"]
avoid   = ["list of specific files/directories Ralph must NOT touch"]
hubs    = ["highly imported files requiring extreme caution"]

[baseline]
test_count     = {number of passing tests before Ralph starts}
test_command   = "just test"
known_failures = []
known_warnings = []

[guardrails]
script = "guardrails-{id}.sh"
```

### 3.2. `guardrails-{id}.sh`
An executable bash script generated by Lisa. Ralph **must** run this and achieve a `0` exit code before he is permitted to call `springfield signal --status success`.
It performs structural checks (e.g., `git diff` against `scope.avoid`) and semantic checks (e.g., test baseline didn't drop).

## 4. Lisa's LRM Planning Loop

Before generating the above artifacts, Lisa executes a Tree of Thoughts (ToT) + Self-Consistency loop.

### 4.1. The Option Evaluation Rubric
For every epic, Lisa must generate at least 2 distinct implementation approaches. She evaluates each against:
1. **ADR Conformance:** Does it violate any established architectural decisions?
2. **Farley Index (Predictive):** Will this approach yield atomic, fast, and repeatable tests?
3. **Adzic Index (Predictive):** Does this approach allow BDD step definitions to remain declarative and uncoupled from implementation?
4. **Retrospective Signals:** Does it mitigate the failures logged in Bart's previous retrospectives?

### 4.2. Self-Consistency Threshold
Lisa runs the evaluation **twice** independently.
- **Stable (2 identical conclusions):** Lisa commits to the approach and generates the `TODO-{id}.md`.
- **Unstable (Differing conclusions):** Lisa runs a 3rd tie-breaker pass. If still fundamentally unstable, Lisa signals `blocked` with `reason=feature_brief_ambiguous`. The orchestrator then invokes Marge to clarify the Intent Layer.

### 4.3. Parallel Epic Management
If the orchestrator spawns multiple worktrees for parallel epics, Lisa tracks her ToT option sets purely via the `Approach Layer` of each `TODO-{id}.md`. If an epic is rejected and returned to her for re-planning, she parses the existing `TODO-{id}.md` to recall her previously rejected alternatives.

## 5. Bart's Dual Output & Retrospective Signal

When Bart reviews Ralph's work, he produces two artifacts:
1. `FEEDBACK.md`: Tactical code review for Ralph (if the PR is rejected).
2. **Retrospective Signal**: A structured payload sent to `td log --decision <epic-id>` for Lisa.

### 5.1. Definition of Epic Closure
An epic is only closed when Bart issues `springfield signal --status success`.
To do so, Bart must verify:
1. All BDD scenarios pass (Product Conformance against the Intent Layer).
2. Ralph's working layer TDD tests pass (Implementation Quality).
3. The guardrails script passes.

### 5.2. Retrospective Signal Schema
Bart must log this payload to the `td` database before signalling success or failure.

```markdown
## Retrospective Signal

### Approach Layer Verdict
verdict: confirmed | partially_confirmed | invalidated
notes: >
  {Context on whether Lisa's chosen approach held up under reality}

### ADR Verdict  
adr_id: {ADR-XXX}
verdict: confirmed | rejected | amended
notes: >
  {Did the architectural hypothesis survive contact with the code?}

### Constraints Revealed
- {Constraint 1 that Lisa should know for the next epic}
- {Constraint 2}

### Tech Debt Signals
- severity: {minor|medium|critical}
  item: {Description of debt introduced or discovered}
```

If the `Approach Layer Verdict` is `invalidated`, Bart signals `blocked` (Option Viability Failure), skipping Ralph and returning the Epic directly to Lisa.
